# UPR-FVX Web

Web frontend for running [Universal Pokemon Randomizer FVX](https://github.com/upr-fvx/universal-pokemon-randomizer-fvx) through its Java CLI. This project was created entirely with OpenAI Codex.

## Requirements

- Node.js 22+
- Java available as `java` on the server path
- A patched FVX JAR placed at `vendor/UPR-FVX.jar`

You can override the JAR path with:

```bash
UPR_FVX_JAR=/absolute/path/to/UPR-FVX.jar npm start
```

## Development

```bash
npm install
npm run dev
```

The frontend runs through Vite and the API server runs on `http://localhost:3000`.

## Settings

The app has two settings modes:

- Visual builder: asks a small Java bridge to generate an FVX settings string through FVX's own `Settings` class.
- Paste string: accepts a full settings string generated by the FVX desktop app.

The visual builder schema comes from a small source patch under `patches/fvx/`. The patch adds
`com.uprfvx.random.web.SettingsMetadata` to FVX, then exposes FVX's settings setters, desktop category/section labels,
and hover help text directly from the FVX codebase. The bridge intentionally requires this patched FVX JAR so schema
generation fails loudly if the web app is pointed at an unpatched release JAR.

For local non-Docker development, build the patched FVX JAR and bridge:

```bash
npm run build:local
```

This downloads the FVX source tag, applies `patches/fvx/`, writes `vendor/UPR-FVX.jar`, and compiles the settings
bridge against that patched JAR. By default it uses FVX `vFVX1.5.1`; override with `UPR_FVX_VERSION`, `UPR_FVX_TAG`, or
`UPR_FVX_OUTPUT` if needed.

The patched FVX JAR build is implemented once in `scripts/build-fvx.sh`. Both `npm run build:fvx` and the Dockerfile
call that script.

## Production

```bash
npm install
npm run build

```

## Docker

The Docker image downloads the FVX Linux release zip for its bundled `data/` directory and Java runtime. It then calls
`scripts/build-fvx.sh` to download the matching FVX source tag, apply `patches/fvx/`, and build the patched FVX JAR.
Finally, it compiles the settings bridge against that patched JAR and runs the web server with the bundled Java binary.

```bash
docker build -t upr-fvx-web .
docker run --rm -p 3000:3000 upr-fvx-web
```

By default the image downloads FVX `vFVX1.5.1`. To build a different FVX release, pass matching build args:

```bash
docker build \
  --build-arg UPR_FVX_VERSION=1.5.1 \
  --build-arg UPR_FVX_TAG=vFVX1.5.1 \
  -t upr-fvx-web .
```

The Dockerfile supports `linux/amd64` and `linux/arm64` targets by selecting the matching upstream Linux asset.

Useful environment variables:

- `PORT`: server port, default `3000`
- `UPR_FVX_JAR`: FVX JAR path, default `vendor/UPR-FVX.jar`
- `JAVA_BIN`: Java executable, default `java`
- `UPR_WEB_TMP`: temp directory, default `tmp/`
- `MAX_ROM_SIZE_BYTES`: upload limit, default `1073741824`
- `RANDOMIZER_TIMEOUT_MS`: CLI timeout, default `300000`

## API

`POST /api/randomize`

Multipart fields:

- `rom`: required ROM file
- `settingsString`: required FVX settings string
- `seed`: optional integer
- `saveLog`: optional boolean, defaults to `false`

When `saveLog=true`, the server returns a zip with the randomized ROM and log. Otherwise it returns the randomized ROM directly.

## Privacy and Legal Note

ROM files are user-provided and are processed in a per-request temporary directory. The server deletes the temporary directory after success or failure. Do not deploy this in a way that logs uploaded ROM content or retains request bodies.
